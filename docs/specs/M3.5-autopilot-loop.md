# SPEC M3.5: Autopilot loop (notify, resume, self-improve, gated submit)

> Status: approved direction, pre-implementation. Written 2026-06-16.
> Builds directly on M3 (WorkdayAdapter verify-or-abstain). Goal: the
> human-touchpoint and submission machinery that turns "fill + verify" into
> the autonomous loop Parv asked for.

## Goal
Run an application end to end with zero human input on KNOWN fields. The only
designed human touchpoints are (1) a genuinely-unknown question and (2) a
captcha. On an unknown question the system fires a macOS desktop notification,
records the question to an inbox, and resumes automatically once the answer is
supplied (which also teaches the AnswerKB so it is never unknown again).
On a green verify AND an explicit approval, it submits and writes a receipt.

## The accuracy + autonomy contract (unchanged invariants)
- Verify-or-abstain (invariant 1): nothing wrong ever reaches an employer. The
  fill+verify maker (WorkdayAdapter) stays submit-free.
- Maker/checker split (invariant 2): submission is a SEPARATE, gated step, not
  something the filler can do. Interface segregation enforces this: the adapter
  only ever holds a submit-free `WorkdayPageDriver`; the Autopilot holds a
  `SubmitDriver` and may submit only after a verified verdict + approval.
- Idempotency (invariant 3): one application per company+role; the event store's
  duplicate-`submitted` guard + a `BatchApproval.idempotencyKey` enforce it.
- EEO/legal (invariant 7): unchanged; only human-approved AnswerKB answers fill
  those, everything else abstains.

## Components
1. **Notifier** (`src/applier/Notifier.ts`): macOS notifications via osascript,
   behind an injectable sink (tests dry-run, demo fires real notifications).
   Kinds: unknown_question, captcha, abstain, batch_complete, error.
2. **AnswerInbox** (`src/applier/AnswerInbox.ts`): the self-improving loop for
   coverage. `flag(question, ctx, why)` appends a pending entry (deduped) to a
   pending file. `resolve(match, value)` appends a human-approved entry to the
   AnswerKB file (config/answers.yml). After resolve, AnswerKB answers it
   forever. This is how human interventions trend to zero.
3. **SubmitDriver** (interface) + WorkdayDriver impl: `clickSubmit()`,
   `readConfirmation()`. Separate from the submit-free WorkdayPageDriver.
4. **Autopilot** (`src/applier/Autopilot.ts`): the orchestrator.
   - run(ctx, opts): run the adapter (fill+verify).
   - abstained -> for each reason: inbox.flag + notifier.unknownQuestion; STOP
     with `needs_input` (caller/demo supplies answers, then re-runs = resume).
   - verify_failed -> notify abstain; STOP (never submit a bad fill).
   - auth_required -> notify captcha/auth; STOP.
   - verified + no approval -> STOP at `ready_to_submit` (fill-only default).
   - verified + approval -> submit via SubmitDriver, write receipt
     (SubmissionRecorder), notify batch_complete. Outcome `submitted`.
5. Fixtures: `tests/demo/fixtures/workday-full.html` (personal + work-auth
   dropdown + start date + an UNKNOWN screening question + EEO section + a
   Submit button that reveals a confirmation id), and
   `tests/demo/fixtures/answers.demo.yml` (non-PII demo AnswerKB).
6. Demo: `scripts/demo-autopilot.ts` runs the whole loop for real against the
   fixture: fill known -> hit unknown -> REAL notification + inbox -> simulate
   the human answering -> resume -> verified -> approved submit -> receipt +
   completion notification.

## Hard safety (this build)
- No real submissions to real employers. The demo submits against the local
  fixture only (a Submit button that reveals a confirmation div, no network).
- Real submission requires an explicit `BatchApproval` and the operator's real
  credentials/session; the apply CLI defaults to fill-only.
- No secrets: demo uses placeholder PII; runs without config/profile.yml.

## Tests first (vitest, pure, no browser)
1. Notifier: dry-run sink receives the right kind/title/message; AppleScript
   string builder escapes quotes/backslashes (pure).
2. AnswerInbox: flag writes a deduped pending entry; resolve appends to the KB
   file; a fresh AnswerKB over that file then answers the question.
3. Autopilot (fake adapter-surface + fake submit driver + dry-run notifier +
   temp inbox/store):
   - abstained -> flags + notifies every unknown, returns needs_input, never submits;
   - resume: after answers added, a second run reaches verified;
   - verified + no approval -> ready_to_submit, never submits;
   - verified + approval -> submits once, writes a receipt, notifies; a second
     approved run is rejected (idempotency), no duplicate receipt;
   - verify_failed / auth_required -> notify, never submit.

## Exit gate
All new vitest tests green; typecheck clean; `npm run demo:autopilot` shows the
full loop reaching a written receipt against the fixture, with a real macOS
notification fired on the unknown question; adversarial review clean; lessons
appended.
